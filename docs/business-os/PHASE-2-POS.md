# Tenant sales and POS — 18 November 2026

The working flagship POS is retained. Migration 064 extends the existing POS tables and constrains old privileged helpers with the legacy executor boundary before opening tenant access. New records use composite tenant/location/customer/session foreign keys and the established private tenant executor.

The new `/company/<slug>/pos` workspace supports named registers, opening cash, cashier sessions, product/SKU/barcode search, variants, cart quantities, price changes with protected-price approval, configurable version-snapshotted tax, sales channels, exact split tender, cash given/change, customer credit limits and due dates, partial/full payment allocations, held carts, printable receipts, inspected returns, separate damaged returns, partial/full refund records and counted drawer closing with variance. Return amounts allocate line tax cumulatively so a full return credits the exact original total. Cashier stock changes consume available stock without consuming ecommerce reservations.

Manual bank/terminal records require finance authority and explicit confirmation of received funds and actual references. They are labelled staff-confirmed and never represented as provider verification. Cash and collection records remain separate from payment promises. Closed sessions cannot accept new sales. Drawer expected cash uses net cash received minus actual cash refunds, excluding bank and terminal tenders.

Cash sales are encrypted in IndexedDB with non-exportable AES-GCM keys before submission. Ciphertext is authenticated against tenant/user/key/status/time metadata. Queue entries retain their original UUID across network errors, reconnects and repeated submissions; server idempotency is actor/payload-bound. Web Locks serialize device-tab synchronization where available, with IndexedDB uniqueness as a second boundary. Pending/review rows are never automatically pruned; the latest 100 server-confirmed local records are retained. Cancellation first waits for the server's matching command lock and checks whether the transaction committed. Rejected transactions remain visible for manual resolution. A drawer cannot be closed through this device while its queue is unresolved.

Offline entry currently applies to a fully paid cash sale in an already opened POS tab. Non-cash/credit actions require connectivity. Reconnection revalidates membership, location grants, session, stock, price and expected tax-inclusive total. Local records are explicitly pending until the server confirms them; conflict resolution never silently forces an oversell or changes a customer payment. An offline cold start or a cleared/corrupted browser profile is not claimed recoverable; keep the tab/profile and synchronize before changing devices or closing shifts. The app cannot guarantee storage against a user deleting browser data.
